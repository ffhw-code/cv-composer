## [2026-09-26] 「`tool-error-retry` 场景重设计」的归口判定（分析，非测量）

测试环境：不适用；核对基准 HEAD = `4580a74`

测试结论：**性质上是 `P0` 的测量基础设施（harness 场景），不是 `P3` 的达标口径要求；但 `P0.1` / `P0.3` 现写的验收条件并不依赖它 —— 它目前处于「没有消费者」状态，需老板指定落法。建议落法 2。**
数据有效性：有效（结论为文件与代码比对，无量化数字）

### 一、核对到的事实

1. **场景现状**（`baseline/aiBaseline.run.ts:120-126`）：prompt 硬要求调用 `set_style` 去改一个不存在的 id（`NOT-EXIST-MODULE-999`），并明说「不要检查模块是否存在」。`glm-5.2` / `deepseek` 会拒绝这种调用（`04-AI链路与成本指标.md` 第六节：命中率 0/3），**量不到「结构化错误 → 重试 → 自愈」这条链**。
2. **`P0` 大阶段的目标确实覆盖它**：`docs/plan/长期优化方案.md` 写 `P0` 要让链路「有调用就有结果、有错误就归对因」；`P0.2` 改动清单第 1 项的守卫设计理由**直接引用该场景的证据**（「缺了它模型缺新信息仍会重试，**历史实测重试自愈率为 0**」→ 所以要回传上一次结果摘要）。
3. **但 `P0.1` / `P0.3` 的验收不依赖它**：`P0.1` 采集集是 `add_module,generate-resume`（6 轮），其 5 项指标与 `P0.3` 的三条判定（打满轮次不再记 `success` / `redundant` 被拦 / 次数·tokens·成功率不劣化）都能用这两个场景覆盖；`P0.2` 第 3 项「三类静默假成功防护」也只靠 `src/**` 单元测试验证。
4. **`P3` 的口径也不含它**：标准 3 只测「工具级正确调用率 / 结果级成功率」，没有「报错后自愈」这一项，故 `P3.1` 建指令集时并无硬性需要。
5. **历史锚定**：旧 `docs/quality/04` 第五节修复计划与旧 `docs/plan/验收口径-交付标准与达标判定.md:122`（工时表 A3）都把它挂在旧口径的「`P0`（AI 链路修复）」。

### 二、三个落法（含利弊）
