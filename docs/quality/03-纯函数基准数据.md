> 本文件是**记录区**：11 项纯函数热路径基准的基线数据、判定阈值、复测记录。
> 内容来源：原 `METRICS.md` 第六节 + 早期 QA 报告（`TASK-000-I` 测试项 5、`TASK-018-I`）。**数值未改动。**

**运行方式**：`npx vitest bench`（11 个 bench，约 10 秒，未引入任何新依赖）。覆盖 `layoutEngine` / `layoutTreeNormalizer` / `moduleUtils` 三个纯函数模块。

**基线的日期与 commit**（2026-09-16 由 QA 补记，属文档补记、**未改动任何数值**）：下表采集于 **2026-09-10**，对应 commit **`26df0eb`**（`test: 新增纯函数热路径基准（vitest bench）并记录基线数据`），经 `git log` 反查确认。

**设计说明**：`normalizeLayoutTree` 与 `applyOverflowCompression` 都会**就地修改输入**，因此每次迭代在 callback 内重新构造输入，确保测到的是「首次规范化」路径；为此单列一条「对照：仅构造输入」，净耗时取两者之差。其余被测函数是纯函数，输入在模块加载时构造一次。

## 二、结论

1. **组内 rme 严重低估真实波动**：tinybench 报告的 rme 最大只有 ±7.3%，而同一 bench 的 run 间跨度最高达 42.3%（`getAllModuleIds`）。判定改动必须用 run 间跨度，**不能引用 rme**。
2. **各 bench 的可用性差异极大**：`computeLayout`、`findModuleById`、`normalizeLayoutTree` 跨度都在 7% 以内，适合做判定依据；`getAllModuleIds`（42%）与 `getCanvasStateSummary` 典型规模（33%）噪声过大，只能看大方向。
3. **净耗时拆分**：`normalizeLayoutTree` 的 26.9 µs 中含 2.1 µs 输入构造（约 8%），净规范化约 24.8 µs——构造开销占比不高，不影响该指标对改动的敏感度。
4. **负结果同样有价值**：`computeLayout` 只要 0.1~0.4 µs，分页计算不是性能瓶颈，不值得投入优化。
5. **最值得关注的热路径**：`getCanvasStateSummary` 典型规模 23.2 µs，是 AI 每轮请求都要跑一遍的函数，且比 `findModuleById` 慢约 1.7 万倍；优化它的收益远大于优化树查找。

---

## 三、使用建议

- 正式判定改动时跑 ≥ 5 轮取中位数，阈值取上表；低于阈值记为「无显著变化」。
- 测量期间避免并行跑其它重负载任务；本次三轮为连续背靠背执行，已属于较理想条件，跨度仍有两位数百分比，说明该机器（WSL2）本身偏噪声。

| 哨兵 bench | 基线中位 (ops/s) | 选它的理由 |
