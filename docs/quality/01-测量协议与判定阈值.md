## 一、测量协议

- **环境固定**：同一台机器、同一 Node 版本、同一条命令；测量期间不做其它重负载操作。
- **重复采样**：每项指标连续测 N 次（N ≥ 3），丢弃第 1 次（冷启动），取中位数。
- **计时口径**：脚本用 `date +%s%N` 记录 npm 命令的墙钟时间；测试内部用时取 vitest 自报的 `tests` 字段。
- **绑定 commit**：每条记录必须写明 commit（base→head）、命令与机器，不能只记日期，否则事后无法解释。
- **环境隔离**：CI（GitHub Actions runner）的耗时噪声远大于本机，两者不混用、不互相比较。

## 三、噪声区间与判定阈值

| 指标 | 中位数 | 实测波动范围 | 相对中位的跨度 | 建议判定阈值 |
|---|---|---|---|---|
| JS 产物体积 | 836185 B | 逐字节一致 | 0% | 任何字节变化都真实 |
| JS gzip 体积 | 258809 B | 逐字节一致 | 0% | 任何字节变化都真实 |
| 用例数 | 240（2026-09-10 实测值） | 一致 | 0% | 任何变化都真实 |
| tests 内部用时 | 400 ms | 398 – 428 ms | 7.0% | > 10%（主指标） |
| 构建墙钟 | 4057 ms | 3583 – 4317 ms | 18.1% | > 20% |
| tsc --force 墙钟 | 3235 ms | 3231 – 3776 ms | 16.8% | > 20% |
| 测试墙钟 | 1515 ms | 1484 – 1872 ms | 25.6% | > 25%（仅记录，不作判定） |
| lint 墙钟 | 4936 ms | 4543 – 5609 ms | 21.6% | > 40%（样本仅 3 个） |

阈值取「实测跨度 × 1.1 ~ 1.9」，即必须明显超过当前观测到的噪声才算信号。由此得到五条使用规则：

1. 体积类与用例数指标是精确值，可以直接写「从 X 降到 Y，减少 Z%」。
2. 耗时类指标必须超过上表阈值才可断言优化。例如构建从 4057 ms 变成 3900 ms 属于噪声，不能称为优化。
3. 构建墙钟最初按 > 10% 设定偏乐观（实测跨度已达 18.1%），已上调至 > 20%；测试墙钟实测跨度 25.6%，上调至 > 25% 并降级为辅助指标（跨度主要由首采冷启动贡献，丢弃首采后仅 5.6%，但 5 个样本不足以据此收紧）。
4. 主指标仍是 `tests` 内部用时（跨度 7.0%）；墙钟时间仅作辅助参考。
5. **用例数变化时，`tests` 用时必须按用例数归一化后再比较**（否则「加了测试」会被误读成「测试变慢」）。
6. **用例数是动态值**：上表 `240` 是 2026-09-10 的实测样本，不是「当前基线」。判定「用例数是否低于基线」一律以 `docs/plan/长期优化方案.md` 最新记录为准（2026-09-17 实测为 **324**）；不得再用 240 做判定。

> **判定纪律**：低于阈值一律写「无显著变化」。凡采样时机器状态与历史行不等价（见第四节哨兵），该行耗时值一律标 `suspect`，**不得作为任何任务的改前基线，也不得作为优化结论引用**。

## 四、环境哨兵规则 v1（**已生效** · 老板 2026-09-26 拍板）

> 背景：2026-09-16 出现过一次「同一份源码、同一条命令，两次采样相差 1.85 倍」的宿主漂移（证据见 `02-工程指标记录.md` 第五节）。
> **生效状态**：老板 2026-09-26 拍板转正，本节自即日起是协议区正式条款；「草案 · 待拍板」状态结束。历史采样行的实际做法（同场复测哨兵并标 `r`）与本节一致，**历史数值与结论一律不变**。

```
哨兵规则 v1（协议区正式条款，2026-09-26 生效）
1) 采样方式：每轮耗时采样前，同场先跑一遍 `npx vitest bench`（现有 11 项 bench，约 10~12 s）；
   取其中 `computeLayout`（12 模块）与 `findModuleById`（命中末节点）两项，各按「连续 3 次、丢弃首采、取中位」取值。
2) 哨兵比：r = 本次哨兵中位 / 基线哨兵中位（基线固定为 2026-09-10：`computeLayout` 12 模块 7,338,741 与
   `findModuleById` 2,187,720）。两项各算一个 r，取较小者作为本次机器的 r（偏保守，倾向承认机器偏慢）。
3) 判定：
   - r ≥ 0.90 → 机器稳定态：耗时值直接与历史行比较；
   - r < 0.90 → 机器变慢：先归一化 t_norm = t_measured × r，再与历史行比较；归一化后仍超阈值才算代码信号；
   - r > 1.10 → 机器变快：同样归一化（否则会把「机器变快」误判成优化）。
4) 记录要求：每条耗时记录必须写明当次 r；未标 r 的耗时值一律按 suspect 处理。
5) 哨兵自身噪声带：单项 run 间跨度历史 1.9%~4.6%、安静态实测 1.8%~7.9%，故单项 ±10% 带内视为「无漂移」。
```

**利弊**：

- 利：0 token、秒级；能立刻区分「代码变慢」与「机器变慢」；只用现有命令，不引入新依赖。
- 弊：哨兵与被测命令不完全线性相关（哨兵是 CPU 密集的纯函数，`vite`/`eslint` 偏 I/O 与模块图遍历），归一化是近似；只能消整体漂移，消不掉「只有部分子系统变慢」的情形；每轮多约 12 s 开销。
- 对历史行的影响：**零**。已落库数值与结论都不变，只影响未来新行的判定方式与备注内容。

## 五、AI 采集的测量条件与成本红线

> 与噪声阈值无关，但属「测量条件」的一部分，采集前必须逐条确认。

- **只有测试会话（TRD）能发起 AI 调用**（经 harness）；Key 只经环境变量 `AI_BASELINE_KEY` 传入，**绝不写入任何文件**。
- **三件套守卫必须显式设置**：`AI_BASELINE_SCENARIOS`、`AI_BASELINE_ITERATIONS`、`AI_BASELINE_MAX_TURN_TOKENS`（默认 30k）；自定义输出目录 `AI_BASELINE_OUT_DIR` 用绝对路径。
- **禁止使用默认档位 `qwen-max`**（免费额度账号开箱即 403）。已实测可用档位：`qwen3.7-flash`（改前基线）、`glm-5.2`（P0-B 验证）、`deepseek-flash`（官方端点）。
- **采集期间不得更换模型档位**：换档位属测量条件变更，新旧数据不得混用（见第六节）。
- **余额必须按渠道确认**：DeepSeek 官方 Key 与阿里云百炼额度是**两本账**，互不相通。
- **执行前两条齐全**：老板确认**本次预算上限**非 0 + 老板确认**对应渠道**的当前余额（两本账，互不相通）。
- **数据有效性**：传输失败占比 > 20% 标 `suspect`；某场景有效轮数为 0 标 `incomplete`（判定规则由 `P0.2` 第 6 项落地，见 `06-AI基线采集手册.md` 第四节）；守卫终止标 `aborted`，**必须如实保留，不得粉饰**。

## 七、口径细节备忘（易错点）

1. **gzip 双轨**：本协议口径是 `gzip -c <file> | wc -c`（入口 263,765 B）；vite 自报入口 gzip 为 268.06 kB。两者压缩级别/实现不同，**不可混用**。历史行统一按前者。
2. **分块产物**：历史行未写明「JS 字节」是否含分块。当前构建产出入口 + `resumeParser-*.js` 两个 JS 文件，记录时以「入口字节 + gzip」为准，分块单独记录。
3. **构建墙钟波动主要来自 `tsc -b` 增量缓存**：实测四轮 `vite build` 自报 497/454/489/461 ms 很稳，墙钟波动几乎全部来自 `tsc -b`（组内跨度最高 97.9%），故构建采样必须保持 ≥ 3 个有效样本。
4. **`.tsx` 测试会被 vitest 静默忽略**：`test.include` 只匹配 `src/**/*.test.ts`；测试文件必须是 `.ts`。
5. **类型检查只有 `npx tsc -b` 有效**：根 `tsconfig.json` 是空壳，`npx tsc --noEmit` 对真实类型错误也返回 0。
