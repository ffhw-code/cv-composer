## 三、逐项方案

### 优化项 1｜`scripts/metrics.mjs` 工程指标自动采集（测试会话）

**依据**：工程指标目前靠人工采集、环境哨兵靠人工同场跑 bench 并标 r（易漏采、易有偏差）。

- **做什么**：自动采集构建 / 测试 / lint 指标，写 `metrics/<sha>.json`，并由脚本生成指标主表的表格行（`docs/quality/02-工程指标记录.md`）。
- **建议一并脚本化**：**环境哨兵**（目前每次耗时采样靠人工同场跑 bench 并标 r，容易漏）。
- **价值**：把「连续 3 次、丢弃第 1 次、取中位数」的协议变成脚本行为，减少人工偏差与漏采样。
- **注意**：脚本属采集类，归测试会话；产物写 `metrics/`（本地不入库），结论落 `docs/quality/02`。

### 优化项 2｜工具 schema 收敛与瘦身（工作会话）

**依据**：请求体积与工具 schema 两处问题：

- 工具 schema 体积 **9,387 字符/请求**（26 个工具），占单请求 prompt 的绝大部分 —— 而单请求 prompt 固定约 **3.46~3.49k tokens**，prompt 占整轮 token 的 **97.2%**（改前基线实测）。
- `set_style` 嵌套参数 schema 未收敛。
- **方向**（详细设计待开工前补）：精简描述文案、去掉冗余枚举、收敛 `set_style` 的嵌套结构；**不得改变工具语义与 `argsStatus` 语义**。
- **风险**：改 schema 会改变请求形状 ⇒ 与历史 AI 数据**不可比**，效果必须由测试会话重新采集对照。

### 优化项 3｜`utils → components` 跨层依赖（**不排期**）

**仅记录**：除老板点名，否则不动。

2. 优化项 2：四项全绿；用例数不低于当时动态基线；请求体 schema 字符数给出改前 / 改后对照；AI 效果变化由测试会话采集后判定（**不得自行宣称优化幅度**）。
