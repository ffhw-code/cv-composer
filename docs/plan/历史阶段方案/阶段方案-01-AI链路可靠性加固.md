## 一、阶段目标

把 AI 链路上「**看起来成功、实际没干活**」与「**出错了但归因错**」两类问题治掉，并让测试基础设施（harness）与真实链路行为一致。本阶段不改产品功能，只改**可靠性**：

1. 同一轮里同一工具被反复调用、打满 8 轮却被记为成功 → **守卫 + 正确计数**；
2. harness 写死的 `tool_choice` 与浏览器侧不一致 → **复用同一处开关**；
3. 工具报错测不到（`glm-5.2` 拒绝按指令调用不存在的 id）→ **换输入变体重设计场景**；
4. 额度类 403 被译成「API Key 没有访问权限」→ **按 `error.code` 分流归因**；
5. harness 只看总传输失败比例、且无总预算上限 → **补完整性判定与总额度守卫**；
6. 三类「静默假成功」→ **加防护与提示**。

> **背景（避免重复讨论）**：DeepSeek 官方接入路线 —— R1「换渠道」**未采用**（老板已定走官方端点）；R2「`tool_choice` 按服务商可配置 + deepseek 预设」**已落地**（`TASK-015`，`6435a60`）；R3「思考模式可控 + 思考内容过滤」**部分落地**（quirks 开关已做；**思考内容的显示层过滤未做**，归优化项 7）。

## 三、逐项方案

### 优化项 1｜同轮重复工具调用守卫 · 改前基线（测试会话）

**为什么**：没有改前数据，「优化了 X%」就是编的。这是优化项 2 的前置门禁。**必须在「请求形状切换点」之后执行**（`TASK-015` 修掉了 `isUpload` 恒真；切换前后请求形状不同、不可比）。

- **测试对象**：`src/components/AI/useAiChat.ts` 的 `MAX_TOOL_ROUNDS = 8`，以及「同一轮内同一工具以等价参数反复调用」时的现有行为（改前状态）。
- **采集档位**：`deepseek-flash`（官方端点 `https://api.deepseek.com`）。依据：探针已实测该档位可用（非上传轮次发 `tool_choice:'auto'` 返回 200 与 `tool_calls`）。**采集期间不得更换档位。**
- **测量指标**（只测本任务要改的）：
  1. 单轮工具调用次数（平均值与最大值）—— 历史证据：`add_module` 场景单轮最高 **14 次**；
  2. 单轮 token 消耗（含 `generate-resume` 单轮最高 **51.5k** 的历史样本）；
  3. 工具调用成功率与参数解析分布（正常 / 修复 / 不可用）；
  4. **打满 `MAX_TOOL_ROUNDS` 的轮次占比**，及这些轮次的 `turn.outcome` 分布（核心证据面：证明「打满却记为 success」确实存在）；
  5. `redundant_call` 计数（当前应为 0，用于对照改后新增的计数）。
- **采样要求**：`AI_BASELINE_SCENARIOS=add_module,generate-resume`、`AI_BASELINE_ITERATIONS=3`，共 **6 轮**；同一档位、同一机器背靠背执行。
- **环境**：本机；需真调模型；Key 只经环境变量 `AI_BASELINE_KEY`；必须显式设置三件套守卫。
- **额度预算**：**40 万 tokens**（依据：同档位历史实测约 5.4 万 tokens/轮（打满 8 轮）× 6 轮 ≈ 32 万，加约 25% 余量）。中途若单轮显著超出该量级 → 立即停手报老板，**不得自行加预算**。
- **验收标准**：
  1. 六轮全部完成，或如实标注 `abort` / 不完整（**不得**把残缺数据当基线）；
  2. 五项指标各有数值与原始证据，写明 commit、档位、命令、机器；
  3. 明确给出「改前是否确实存在打满 8 轮且记为 success」的判定；
  4. 报告不出现 Key；
  5. 数据落库后由工作会话在 `长期优化方案.md` 第四节「阶段索引」的状态列标注「基线已冻结」；**在此之前优化项 2 不得开工**。

### 优化项 2｜同轮重复工具调用守卫（工作会话）

**依据**：同轮重复工具调用无守卫（P0）。

**设计（四层，已完整）**：

1. **指纹去重**：`fingerprint = toolName + ':' + stableStringify(args)`。`stableStringify` 需**按键名排序、剔除 `undefined`、数组保序**（数组顺序有语义）。同一轮内第二次出现同一指纹即判为冗余。
2. **冗余响应**：不执行 handler，直接回传结构化结果 `{ ok: false, code: 'REDUNDANT_CALL', message: '该调用在本次对话中已执行过', priorResult: <上一步结果摘要> }`。
   **关键点**：必须把**上一次的结果摘要**带回给模型，否则模型缺少新信息仍会重试（历史实测重试自愈率为 0）。
3. **语义守卫（仅 `add_module`）**：当标题与内容都相同的模块已存在时返回 `{ ok: false, code: 'REDUNDANT_MODULE', existingId }`，不再新建 / 删除（治理 add→remove 抖动）。
4. **计数修正**：`AiToolEvent.errorKind` 增加 `'redundant_call'`；新增 `turn.redundantCalls`；`MAX_TOOL_ROUNDS` 打满时 `turn.outcome` 判为 `partial`（**不再记为 `success`**）。

**接口纪律与边界**：

- **不改 `argsStatus` 语义**（它只描述参数解析结果）；冗余一律走 `errorKind`。
- 合法的「先 remove 再 add」指纹不同，不得误拦；模型自造随机 id 时指纹不同、拦不住（依赖第 3 层）；批量改同一模块的不同属性参数不同，安全。

**允许改动文件**：`src/components/AI/useAiChat.ts`、`src/utils/aiMetrics.ts`、`src/engine/toolHandlers.ts`（仅为 `add_module` 加同名守卫，改动最小）、对应的 `src/**/*.test.ts`（新建测试**不得**用 `.tsx`，vitest 会静默忽略）。**不得**改 `baseline/**`。

**验收条件**：

1. 四项全绿，且用例数不低于**当时的动态基线**（2026-09-17 为 **324**；卡内旧文写的 304 是三会话时期写法，已作废），必须粘贴 vitest 自报的 `Test Files N passed` 与 `Tests M passed` 原文；
2. 新增单元测试覆盖：同指纹第二次调用判冗余且 handler 未执行、`priorResult` 被带回、`stableStringify` 的键序无关性与数组保序、数组顺序不同视为不同指纹、`add_module` 同名返回 `REDUNDANT_MODULE`、打满轮次 `outcome = partial`；
3. **效果验收**（对优化项 1 冻结的基线）：`add_module` 场景单轮工具调用数下降、单轮 tokens 下降、摘要中出现 `redundant_call` 计数、打满轮次不再记为 `success`。采集由测试会话另跑；**本项交付时只给出改前对照的数字位置，不得自行宣称「已优化 X%」**；
4. 交付汇报写明改前/改后行为差异（含被打回的调用示例），不贴 Key。

**额度预算**：0 tokens（本项不真调模型）。

### 优化项 3｜harness 同步「服务商 `tool_choice` 开关」（测试会话）

**问题**：`baseline/aiBaseline.run.ts:503` 写死 `tool_choice: 'auto'`，在 DeepSeek 官方端点下会与浏览器侧一样被拒。

**要求**：harness **复用 `src` 侧的服务商开关**（不复制实现、不另写一套判断），使 harness 与真实链路行为一致；若开关已做成可复用函数，应直接调用。

**测量指标**：harness 在目标档位下能否正常发起请求（成功率）、改前/改后采集数据的可比性。
**采样要求**：先用 1 个场景 × 1 轮做冒烟（确认不再 400），再按后续优化项的要求采集。
**额度预算**：**5 万 tokens**（仅冒烟）；余额未确认时只做 0 token 部分（读代码 / 改 harness / `npx tsc -p tsconfig.baseline.json`）。
**允许改动文件**：`baseline/**`、`vitest.ai-baseline.config.ts`、`docs/testing/测试报告.md`。

**验收条件**：

1. harness 在目标档位下请求成功（附原始状态码为证）；
2. harness 与浏览器链路使用**同一处**开关定义（在报告中指出该函数 / 常量位置）；
3. `npx tsc -p tsconfig.baseline.json` 退出码 0；
4. 报告不出现 Key；
5. **真机复验**：用 1 个场景 × 1 轮验证「非上传轮次真实请求返回 200，且**不出现** `Thinking mode does not support this tool_choice`」—— 这是 DeepSeek 打通那次交付**唯一无法在本地验证**的面。报告附原始状态码与错误体（若有）；若仍返回 400，立即停手、保留原始响应、报阻塞，**不得**自行改 `src/**`。

### 优化项 4｜`tool-error-retry` 场景重设计（测试会话）

**依据**：场景测不到目标链路（P0）。`glm-5.2` 会拒绝按指令调用不存在的 id（命中率 **0/3**），改用「**模块存在但参数类型不对**」的输入才能真正测到「工具报错 → 结构化错误 → 自愈」链路。

**允许改动文件**：`baseline/**`、`docs/testing/测试报告.md`、`docs/quality/**`（数据）。

### 优化项 5｜额度类 403 归因分流（工作会话）

**依据**：额度类 403 归因的两处偏差（P1）：

- 前端把额度类 403 译成「API Key 没有访问权限」；
- 默认模型 `qwen-max` 在「仅免费额度」账号开箱即 403。

**方向**（详细设计待开工前补）：`classifyApiError` / `translateApiError` / 默认模型档位三处分流，按 `error.code` 判断而不是按状态码笼统归类。

**允许改动文件**：`src/**`（具体清单待方案定稿）。

### 优化项 6｜harness 完整性判定 + 总额度守卫 + 预检文案分流（测试会话）

**依据**：harness 完整性与预算守卫缺失（P1）：

- harness 完整性判定只看总传输失败比例 —— 单个场景有效轮数为 0 时也应标不完整（8.6 那轮总传输失败 **15.8%** 未触发 `suspect`，但 `add_module` 实际 0 数据）；
- harness 无总预算上限。

**方向**（详细设计待开工前补）：

1. `incompleteScenarios` 标记，与 `suspect` / `aborted` **三标记独立**；
2. `AI_BASELINE_MAX_TOTAL_TOKENS`，超限落盘终止；
3. 预检文案按 `error.code` 分流（与优化项 5 配套）。

**允许改动文件**：`baseline/**`、`docs/testing/测试报告.md`。

### 优化项 7｜静默假成功防护（工作会话）

**依据**：静默假成功三类（P1）：

3. `</think>`（思考标记）泄漏到正文。

**方向**（详细设计待开工前补）：三类分别加防护与提示；与优化项 2 的 `partial` 判定配合；DeepSeek 思考内容的**显示层过滤**也归此项。
