## 一、目标与判定项

**目标**：标准 1（基础编辑稳定、流畅、可扩展；画布准确、灵敏直观；网页文档流自动排版）**二档达标**。
判定口径取自 `docs/plan/验收口径-交付标准与达标判定.md` 第二节，逐条落成可执行的判定项：

| # | 二档判定项（原文口径） | 本阶段怎么判 | 谁 |
|---|---|---|---|
| A | M 清单全项通过 | 老板在**固定环境**下逐步执行第四节清单，每步填「实际」；WK 记录、TRD 归档 | 老板执行 |
| B | 构建体积与用例数无劣化 | 体积 **≤ 853,817 B**（`5c07275` 实测，精确值＝协议口径 `gzip -c <file> \| wc -c` 见 `docs/quality/02` 第八节）；用例数 **≥ 372**（当前动态基线） | TRD 协议复采 |
| C | 布局幂等性有自动化测试且通过 | 第三节第 1 项新增幂等性测试，四项全绿时通过 | WK |
| D | 画布状态摘要复测无超阈劣化 | `getCanvasStateSummary` bench 重跑：该 bench 噪声跨度 33%、阈值 35% ⇒ **只作趋势参考**，低于阈值写「无显著变化」 | WK 跑、TRD 附哨兵比 `r` |

**两项口径缺口**（标准 1 里目前**没有判定项**）：「**网页文档流自动排版**」与「**可扩展性**」。本方案给出建议判定方式，**由老板拍板**（第二节）；不拍板则这两项只能判「无法判定」，总验收里标准 1 也判不完整。

**一档（可选冲刺）不在本阶段范围**：二档 + 画布状态摘要热路径优化超 35% 噪声阈值 + 60 模块规模无可感知卡顿（老板手动确认）。是否冲一档由老板在收口时定。

## 二、口径缺口：建议判定方式（**待老板拍板，两处独立二选一**）

### 缺口 1｜网页文档流自动排版

现状：README 写明本项目靠 HTML/CSS 文档流（Flex/Grid）实现自动排版；代码侧已有分页（`src/engine/layoutEngine.ts`）、溢出压缩（`src/engine/layoutTreeNormalizer.ts` 的 `applyOverflowCompression`）、等比缩放（`src/engine/layoutScaler.ts` 的 `scaleLayoutToFit`），但**没有任何判定项**。

- **口径 A（推荐：自动化不变量 + 手工各一层）**
  1. **自动化不变量测试**（0 token、新增）：`computeLayout` 分页守恒 —— 每个模块 id 恰好出现一次、顺序与画布一致、每页高度 ≤ 页容量（单模块本身超高除外，**该情形单独断言**）；`scaleLayoutToFit` 仅在总高 > 页容量时缩放、缩放后总高 ≤ 页容量、系数 ∈ (0,1]；`applyOverflowCompression` 压缩后不越界、不改变模块顺序。**不变量以现有实现为准逐条校准；若现有实现不满足某条，记为缺陷（第七节），不得为了测试变绿而放松断言。**
  2. M 清单第 16~18 步（文档流步骤）全过。
  判定：1 + 2 全过。
- **口径 B（只手工）**：仅靠 M 清单第 16~18 步判定，不落地自动化。省事，但不可复跑、无回归保护，且「自动排版」这一条只能凭观感判定。

### 缺口 2｜可扩展性

现状（已核）：样式预设 id 以**字面量**散落在多处 —— `src/engine/aiPrompt.ts:367`（工具 schema 描述）、`src/engine/skillExecutor.ts:239`（技能清单）、`src/engine/templates.ts:75/100/180/206`（模板）、`src/styles/styleInit.ts`（预设实现）；**没有集中的预设清单**（grep 不到 `STYLE_PRESETS` 之类常量）⇒ 新增一个预设要改多处，且无测试保护。

- **口径 A（推荐：单一真源 + 一致性测试 + 演练）**
  1. **建单一真源**：把**样式预设**清单收进一个常量模块（本轮只做样式预设这一类）。
     **硬约束**：`src/engine/aiPrompt.schema.test.ts` 的 `schemaChars = 8,776`、全量哈希 `ced1ec06`、结构骨架哈希 `31a7e0d5`、约束块哈希 `b63c240` **必须一字不变** —— 该测试同时是 `P0.2` 请求形状冻结点的锁；把它改红＝动冻结面，须走解冻流程（老板裁定 + 重跑 `P0.3` 对照）。**只允许「字面量换成引用」，不允许改 schema 文本。**
  2. **一致性测试**：断言预设清单 ↔ 工具 schema 描述 ↔ 技能清单 ↔ 模板 ↔ 样式面板选项**同源一致**，任一处漏改即红。
  3. **M 清单第 19 步（演练）**：走一遍「新增一个样式预设」，记录实际需要改的文件数（预期 1 处）。
  判定：1 + 2 过，且 3 的改动面 ≤ 1 处；若 3 仍显示要改多处 ⇒ 记为缺陷，是否本轮修由老板定（可能超出本阶段范围）。
- **口径 B（只演练）**：不做真源化，只做 3 的记录（按现状预期要改 4~5 处）。风险：可扩展性实际不达标，却因为没有判定项而判不了。

**拍板点**：两处各选 A 还是 B（可各选各的）。**未拍板前不得判标准 1 达标。**

1. **四项全绿**并粘贴实测原文：`npx tsc -b`、`npx eslint . --max-warnings 0`、`npm test`、`npm run build`（`npm test` 必须包含 vitest 自报的 `Test Files N passed` / `Tests M passed`）；
2. **用例数 ≥ 372**（当前动态基线，以 `docs/plan/长期优化方案.md` 最新记录为准）；新增用例必须覆盖：幂等性重放、（选 A 时）文档流不变量与预设一致性、守卫回绕话术；
3. **判定项 A**：M 清单全项通过（本方案第四节填完「实际」列）；
4. **判定项 B**：由 TRD 按 `docs/quality/01` 协议复采（连续 3 次、丢弃第 1 次、取中位数；体积/用例数是精确值，耗时类须附哨兵比 `r`），结果落 `docs/quality/02` 主表；
5. **判定项 D**：`npx vitest bench` 重跑 `getCanvasStateSummary` 两条 case，与 `docs/quality/03` 基线比较，低于阈值写「无显著变化」（须附同场哨兵比）；

## 八、出口规则（失败怎么办）

- **达标**（A~D 全过 + 两项缺口按拍板口径判定）→ 收口，进入 `P2`。
- **不达标** → 按缺陷台账修 → 重跑受影响的判定项；**同类缺陷最多迭代 2 轮**（若用了真调证据，额度上限按老板批的本次预算，触顶即停）。2 轮后仍不达标 → **停下报老板**，由老板裁决：修订口径 / 扩大范围 / 判「不达标」（**不得自行放松阈值或改口径**）。
- **阻塞** → 老板输入未到位、需要动冻结面（解冻未获批）、额度未批 ⇒ 判「阻塞」，如实记录，不硬跑。

## 九、残余风险与边界

- **M 清单是人工判定**：结论带主观性；只有固定环境（浏览器 / 分辨率 / 缩放）才有可比性，环境一换就得重跑。
- **没有 UI 自动化测试**（项目无 playwright / cypress）⇒ 判定项 A 无法自动化，判定项 C / 缺口 1 的自动化只能覆盖**纯函数层**，覆盖不到真实渲染与拖拽手势。
- **缺口 2 的自动化只能证明「清单一致性」**，不能证明架构真的可扩展；最终仍以第 19 步演练的改动面为准。
- **不能碰冻结面**：任何改动若让 `aiPrompt.schema.test.ts` 变红，就是动了 `P0.2` 请求形状冻结点，必须先走解冻流程。
- **不引入新依赖、不动 CI 与 `package-lock.json`、不删既有测试**（`AGENTS.md` 第 8 节）。

4. WK 做优化项 4（守卫话术 + 拍板后的判定）+ 单测；（可选）TRD 真调 1 轮取端到端证据；
