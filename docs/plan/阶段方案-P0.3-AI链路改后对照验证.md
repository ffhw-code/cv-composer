# 阶段方案 P0.3：AI 链路改后对照验证

> **所属**：总方案 `P0` 的小阶段 —— 见 `docs/plan/长期优化方案.md` 第三节。
> **写者**：工作会话（WK）。**执行方**：测试会话（TRD，真调模型采集）。
> **状态**：`已计划`。**前置**：`P0.2` 收口（四项全绿 + 冻结点生效）+ 老板确认预算上限与渠道余额。**不估算工时**。
> 更新：2026-09-27。

---

## 一、目标

在 `P0.2` 的代码上，用与 `P0.1` **逐项相同**的条件复采一次，判定三件事：

1. 打满轮次的轮次**不再记为 `success`** —— 限制：`P0.1` 实测 0/6 打满，该项大概率仍不触发，届时如实写「未复现、无法判定」，由 `src/**` 单元测试背书；
2. **诱导场景 `redundant-call`** 的同轮重复调用**被拦下**（`redundant > 0`、handler 未执行，且该场 `duplicateCalls ≥ 1`）；
3. 单轮调用次数 / tokens / 调用成功率**没有超阈值劣化**。

## 二、怎么采

- 命令、档位、迭代数、`OUT_DIR`、Key 传法、哨兵比 `r` —— **与 `P0.1` 逐项一致**（见 `docs/plan/阶段方案-P0.1-AI链路改前基线.md` 第三节）；`MAX_TURN_TOKENS` **沿用 `P0.1` 实际取值 `60000`**（P0.1 实测单轮最大 10,370，配 60000 以保证逐项一致，不用方案默认 30k）。
- **场景集＝3 个（9 轮）**：`add_module` 3 + `generate-resume` 3（与 `P0.1` 同集，判「无劣化」）+ **`redundant-call` 3**（诱导场景，判「守卫真的拦下过」；改前 3 轮已由 `P0.2` 施工前补采完成，见 `docs/testing/测试报告.md` 2026-09-27 条目）。不含 `tool-error-retry`（归 `P0.2` 第 8 项，只用于其冒烟）。
- **建议预算上限**：**12 万 tokens**（依据：`P0.1` 实测 6 轮 60,502 tokens、单轮约 1.01 万 ⇒ 9 轮约 9.1 万 + 约 30% 余量）；实际上限以老板当场确认的为准。
- 采集期间不得换档位；同一机器、连续跑。**施工前不得改请求形状**（冻结点），否则 `P0.1` 与诱导场景改前数据作废、需重采。

## 三、判定口径（不得自创阈值）

| 指标 | 判定方式 |
|---|---|
| 打满轮次的 `outcome` | **精确值**：出现 `partial` 即生效；仍出现 `success` 即**不达标** |
| **诱导场景**（`redundant-call`，改后 3 轮） | **精确值**：应出现 `errorKind:'redundant'` 的拦截、handler **未执行**、`redundant > 0`；同时该场 `duplicateCalls` 仍应 **≥ 1**（证明模型确实又发出了同指纹第二次调用，而不是「本来就没重复」） |
| **每轮门槛**（诱导场景内） | 某轮 `duplicateCalls = 0`（模型这次不肯连调）⇒ **该轮不可作判据**，属「门槛未过」，如实标注后按剩余达标轮判定；3 轮全 0 ⇒ 判「无法判定」，报老板 |
| `redundant` 计数（2 个常规场景） | **精确值**：> 0 即守卫被触发；须附被打回的调用示例（工具名 + 次数，不含简历正文）。`P0.1` 实测这两个场景 `redundant = 0` ⇒ 这里预期仍是 0，**只能证明「无劣化」，不能证明守卫拦下过** |
| 单轮调用次数 / tokens | 与 `P0.1` 对照给出改前 / 改后 / 幅度；**`docs/quality/01` 未给该指标阈值时只如实记录，不宣称「优化 X%」** |
| 工具调用成功率 | 不得劣化；有变化必须逐条解释 |
| 耗时类 | 按 `docs/quality/01` 第四节阈值判定；同场哨兵比 `r ≥ 0.90` 才能直接与 `P0.1` 比较，否则按 `t × r` 归一化后再判，或标 `suspect` |

## 四、验收条件

1. 完成 **9 轮**（`add_module` 3 + `generate-resume` 3 + `redundant-call` 3），或如实标注 `abort` / 不完整 / 门槛未过；
2. 三件判定逐一给出结论：生效 / 不生效 / 无法判定 + 原因；
3. 数据落 `metrics/`，对照表与结论落 `docs/testing/测试报告.md`；标 commit（`P0.1` / `P0.3` 各一）、档位、命令、样本量、`r`；
4. 报告不出现 Key；
5. 出现「打满仍记 `success`」或「诱导场景里同指纹第二次调用仍被真正执行（`redundant = 0`，且该轮 `duplicateCalls ≥ 1` 已过门槛）」→ 判 **不达标**，停手报老板（按总方案出口规则处理，不得自行改口径）。

## 五、允许改动 / 禁止

- **允许**：`baseline/**`（仅为采集所需）、`docs/testing/测试报告.md`、`docs/quality/**`。
- **禁止**：改 `src/**`（要测的就是 `P0.2` 冻结点上的代码）；把 Key 写进文件。

## 六、完成后

工作会话在老板告知后更新 `docs/plan/长期优化方案.md` 第四节 `P0` 状态（`测试通过` / `不达标`），并在交付汇报里给出 `P0` 收口结论。

## 七、时窗与顺序（2026-09-27 补）

- 诱导场景 `redundant-call` 的**改前** 3 轮必须在 `P0.2` 第 1 项动工**之前**采完；否则产品代码一变就取不到改前数据（不能回滚代码）。**该时窗已于 2026-09-27 闭合**（改前 3 轮 + 门槛冒烟 1 轮已完成，落 `docs/testing/测试报告.md`）。
- 因此执行顺序为：诱导场景改前（已完成）→ `P0.2` 第 1~4、7 项施工 + 收口 → 本小阶段改后复采（3 场景 × 3 轮）。
