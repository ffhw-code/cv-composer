# 阶段方案 P0.3：AI 链路改后对照验证

> **所属**：总方案 `P0` 的小阶段 —— 见 `docs/plan/长期优化方案.md` 第三节。
> **写者**：工作会话（WK）。**执行方**：测试会话（TRD，真调模型采集）。
> **状态**：`已计划`。**前置**：`P0.2` 收口（四项全绿 + 冻结点生效）+ 老板确认预算上限与渠道余额。**不估算工时**。
> 更新：2026-09-26。

---

## 一、目标

在 `P0.2` 的代码上，用与 `P0.1` **逐项相同**的条件复采一次，判定三件事：

1. 打满轮次的轮次**不再记为 `success`**；
2. 同轮重复调用被拦下（`redundant` 计数出现，且 handler 未执行）；
3. 单轮调用次数 / tokens / 调用成功率**没有超阈值劣化**。

## 二、怎么采

- 命令、档位、场景、迭代数、`MAX_TURN_TOKENS`、`OUT_DIR`、Key 传法、哨兵比 `r` —— **与 `P0.1` 逐项一致**（见 `docs/plan/阶段方案-P0.1-AI链路改前基线.md` 第三节）。
- 场景集同样固定为 `add_module,generate-resume`（6 轮），**不含** `tool-error-retry`（该场景重设计归 `P0.2` 第 8 项，只用于其冒烟）。
- **建议预算上限**：与 `P0.1` 同量级（约 40 万 tokens）；实际上限以老板当场确认的为准。
- 采集期间不得换档位；同一机器、连续跑。

## 三、判定口径（不得自创阈值）

| 指标 | 判定方式 |
|---|---|
| 打满轮次的 `outcome` | **精确值**：出现 `partial` 即生效；仍出现 `success` 即**不达标** |
| `redundant` 计数 | **精确值**：> 0 即守卫被触发；须附被打回的调用示例（工具名 + 次数，不含简历正文） |
| 单轮调用次数 / tokens | 与 `P0.1` 对照给出改前 / 改后 / 幅度；**`docs/quality/01` 未给该指标阈值时只如实记录，不宣称「优化 X%」** |
| 工具调用成功率 | 不得劣化；有变化必须逐条解释 |
| 耗时类 | 按 `docs/quality/01` 第四节阈值判定；同场哨兵比 `r ≥ 0.90` 才能直接与 `P0.1` 比较，否则按 `t × r` 归一化后再判，或标 `suspect` |

## 四、验收条件

1. 与 `P0.1` 同样本量完成（6 轮），或如实标注 `abort` / 不完整；
2. 三件判定逐一给出结论：生效 / 不生效 / 无法判定 + 原因；
3. 数据落 `metrics/`，对照表与结论落 `docs/testing/测试报告.md`；标 commit（`P0.1` / `P0.3` 各一）、档位、命令、样本量、`r`；
4. 报告不出现 Key；
5. 出现「打满仍记 `success`」或「同一调用被重复执行」→ 判 **不达标**，停手报老板（按总方案出口规则处理，不得自行改口径）。

## 五、允许改动 / 禁止

- **允许**：`baseline/**`（仅为采集所需）、`docs/testing/测试报告.md`、`docs/quality/**`。
- **禁止**：改 `src/**`（要测的就是 `P0.2` 冻结点上的代码）；把 Key 写进文件。

## 六、完成后

工作会话在老板告知后更新 `docs/plan/长期优化方案.md` 第四节 `P0` 状态（`测试通过` / `不达标`），并在交付汇报里给出 `P0` 收口结论。
