## 一、项目优化目标（终点）

| 标准 | 内容 | 验收下限 |
|---|---|---|
| 标准 1 | 基础编辑稳定、流畅、可扩展；画布准确、灵敏直观；网页文档流自动排版 | **二档必须达标** |
| 标准 2 | AI 解析简历图片，接近 1:1 复刻到画布 | **必须达标一档**：关键字段 ≥90%、版式结构一致度 ≥80% |
| 标准 3 | AI 助手会使用编辑器全部编辑操作 | **二档必须达标**，并**尽量**达标一档 |
| 标准 4 | AI 助手是简历专家，能给出建议与优化 | **只做一轮**主观评估，报告须标注「主观数据」 |

> **档位定义（一档 / 二档怎么算）见 `docs/plan/验收口径-交付标准与达标判定.md` 第二节**；标准 1 / 标准 3 的档位定义仍是起草稿，**待老板确认**（见该文件第二节与第六节）。

## 二、项目现状（起点）

`cv-composer`：聊天式 AI 简历编辑器（React 19 + TypeScript + Vite 8 + Zustand 5 + TipTap 3 + Tailwind 4 + dnd-kit）。**纯前端，无后端**；AI 请求由浏览器直连模型服务商；部署 GitHub Pages。

- **形态**：纯前端、无后端；AI 请求由浏览器直连服务商；API Key 只存在浏览器当次会话。
- **能力边界**：简历图片复刻目前只有单步流程；PDF / Word 直接报错；AI 链路存在「同轮重复工具调用、打满轮次却记为成功」等可靠性问题（即阶段 1 要治的对象）。
- **验收状态**：**四项交付标准均未验收**；验收测量（阶段 2）被阶段 1 与额度前置卡住。
- **工程侧**：四项全绿（2026-09-27 实测）；用例数动态基线 **372**（2026-09-27，含 `P0.2` 新增的 48 个用例）；体积 / 耗时等指标的原始值与判定见 `docs/quality/02`（`P0.2` 改动后的体积需由测试会话复采，本文件不预判）。HEAD 属易变事实，以 `git log` 实时为准，本文件不记录。

## 三、总优化方案

> **当前状态：已定（老板 2026-09-26 拍板，含审核补充的 8 处）。**
> **编号口径**：`P0` / `P1` / `P2`… 是**大阶段**，按优先级与依赖排序（P0 最高）—— **编号即优先级顺序，不再另标优先级**；`P0.1` / `P0.2`… 是它的小阶段。
> **两层结构**：本节只定大方向与大阶段边界；到了「不再细分」的层级（不细分的大阶段，或细分后的小阶段），每个层级各出一份阶段方案写具体做法 —— 阶段方案由本方案推导得出，本方案不引用任何既有方案文件。**阶段方案未制定并经老板确认，任何阶段不得开工。**
> **细分规矩**：一个大阶段能一次做完（只在最后测一次检验成果、中间无需停下来测或决策）就不细分；中间必须停下来测一次或决策一次的，才拆成小阶段。**工时不作估算**（老板 2026-09-26 作废该指标）。
> **额度决策点**：含真调模型采集的阶段（`P0.1` / `P0.3`、`P2.1` / `P2.3`、`P3.1` / `P3.3`、`P6`）开工前，须由**老板**确认本次预算上限与对应渠道余额（DeepSeek 官方与阿里云百炼是两本账）；未确认不得开工；中途出现超预算迹象立即停手报告。

**P0｜AI 链路可信化与请求形状冻结**（细分 P0.1~P0.3）

- 目标：让 AI 链路「有调用就有结果、有错误就归对因」，并把发给模型的请求形状固定下来。
- 为什么最先：后面每一项 AI 结论都从这条链路测出来 —— 链路会假成功、或 harness 与真实链路不一致时，测出的「达标」不可信；守卫与 schema 都会改变请求形状，必须在任何达标采集之前落定。
- token 口径：**只有 `P0.2` 是 0 token**；`P0.1` / `P0.3` 真调模型。
- 收口与冻结点：设**请求形状冻结点**，冻结的是**标准 3 测量所用的工具调用链路**（26 个工具 schema、轮次上限语义、system prompt 的约束块）；`P2.2` 的解析链路不在冻结范围。若后续修复必须动冻结面，走**解冻流程**：说明改了什么 → 重跑 `P0.3` 的同场景对照 → 之前用旧形状采集的数据标「不可比、需重采」。

**P0.1｜改前基线**

- 真调模型采集同轮重复调用、打满轮次、静默假成功的改前数据（一次采集，采集期间不换档位）。

**P0.2｜施工与自测**

- 同轮重复调用守卫与计数修正、打满轮次不再记成功、三类静默假成功防护、额度类 403 归因分流、harness 与浏览器链路共用同一开关、harness 完整性判定与总额度守卫、工具 schema 收敛（26 个工具 9,387 → 8,776 字符 / 请求）；交付四项全绿。

**P0.3｜改后对照验证**

- 同场景复采，与 P0.1 对照，确认守卫生效、打满轮次不再记为成功。

**P1｜编辑地基达标（标准 1）**（不细分）

- 目标（**阈值是暂定值，标准 1 档位口径经老板确认后冻结**）：布局幂等性有自动化测试且通过、画布状态摘要复测无超阈劣化、M 清单全项通过。
- 口径缺口：标准 1 里的「**可扩展性**」与「**网页文档流自动排版**」目前没有独立判定项（M 清单只部分覆盖文档流排版）—— 需老板确认口径，或由本阶段阶段方案补测量方式；不补则这两项只能判「无法判定」。
- 为什么在这里：0 token、成本低，而标准 2 / 3 的结论都落在画布上 —— 地基不稳会把画布缺陷误读成 AI 不达标。
- 依赖：无；可与 P0 并行，但结论须先于 AI 采集。M 清单由老板按固定浏览器与分辨率执行留痕。
- 前置：标准 1 档位口径确认（未确认不得判达标）。

**P2｜标准 2 复刻达标**（细分 P2.1~P2.3）

- 目标：关键字段准确率 ≥90%、版式结构一致度 ≥80%。
- 为什么排在 P3 之前：P2.1 很便宜，却决定「后端是否需要做、要做多少」，先做可避免后端做两遍、采集重跑。
- 依赖：P0 的冻结点；**P1 结论已出**（未发现会把画布缺陷误读成 AI 不达标的问题）；素材需老板提供（≥5 张真实简历图 + 字段标准答案）。

**P2.1｜CP-1 可达性检查点**

- 内容：2 张真实简历图 × 单步 / 两步流程各 1 轮（约 4~8 万 tokens）。
- 两步流程口径：**本小阶段不改产品代码**，用 harness 串两次调用模拟两步（先提文字、再把文字 + 原图构建版面）；若 harness 撑不住，则先做 `P2.2` 的「两步流程最小实现」，`P2.1` 基于它测。
- Go / No-Go 判据（老板 2026-09-26 拍板）：两步流程的关键字段准确率 **≥90% → Go**（走前端路线）；**未达 90% 但显著优于单步 → 条件 Go**（需在 P2.2 / P2.3 证明能迭代到 90%）；**否则 No-Go**（启用 P4，或请老板重议一档口径）。结论必须落文件，作为 P4 是否启用的依据。

**P2.2｜改造复刻链路**

- 按 P2.1 结论做解析 prompt 与示例、两步流程、PDF / Word 支持；若判 No-Go，则先做 P4。

**P2.3｜采集迭代至达标**

- ≥5 张图 × 3 次取中位数，迭代到一档；迭代次数与额度上限由本阶段阶段方案定，触顶即按出口规则处理。

**P3｜标准 3 工具调用达标**（细分 P3.1~P3.3）

- 目标（**阈值是暂定值，标准 3 档位口径经老板确认后冻结**）：二档必达（核心写操作工具 ≥90%、查询 / 导出 / 技能类 ≥70%、结果级成功率 ≥70%）；尽量冲一档（全部 26 个工具 ≥90%、结果级 ≥85%）。
- 依赖：P0 的冻结点；**P1 结论已出**；档位固定、同一次采集不换档；额度按实际档位重算。
- 前置：标准 3 档位口径确认（未确认不得判达标）。

**P3.1｜指令集与首轮采集**

- 26 个工具各 1~3 条中文指令，首轮采集同时作改前数据。

**P3.2｜修复**

- 修工具级与结果级正确率；若必须动 P0 的冻结面，走解冻流程。

**P3.3｜复测判二档**

- 复测一轮判二档；不过则按出口规则处理。一档冲刺单列（若需更强模型，排在 P4 之后）。

**P4｜后端能力（密钥代理 + 图片与文档预处理）**（不细分，按需启用）

- 目标：服务端密钥代理（浏览器不再持有长期密钥）+ 图片与文档预处理；视需要再扩展到服务端模型路由与降级。
- 按需判据：`P2.1` 判 No-Go，或 `P3.3` 一档冲刺需更强模型时才做；否则降为可选增强，不阻塞主路径。
- 位置：**可动态插入**（`P2.2` 之前，或 `P3.3` 一档冲刺之前），插入后其后各阶段的先后随之调整。
- 前置：老板三项输入（服务端平台 / 是否引入第三方 OCR 或视觉服务 / 密钥托管）。

**P5｜工程采集自动化**（不细分，空档插入）

- 目标：工程指标一键复采（含环境哨兵脚本化），把「连续 3 次、丢弃第 1 次、取中位数」变成脚本行为。
- 位置：0 token、无前置，可插入任一大阶段的空档；不做也不阻塞达标。

**P6｜标准 4 主观评估与总验收收口**（不细分）

- 目标：一轮主观评分（≥5 份简历、报告标注「主观数据」，不与客观指标混算）+ 四项标准逐条判定；原始数据落 `docs/quality/**`、结论落 `docs/testing/测试报告.md`。
- 标准 4 口径：按验收下限执行 —— 只判「**已完成一轮主观评估**」，不设能力达标线。
- 依赖：P0~P3 收口；P4 若启用则一并收口；**P5 可选，不构成依赖**。判定还要求标准 1 / 标准 3 的档位口径到位、以及（若启用 P4）三项输入到位，否则相关标准只能判「无法判定」。

**出口规则（达标阶段的失败出口）**

- **达标**：按该阶段口径判定通过 → 进入下一阶段。
- **不达标**：先按该阶段阶段方案定的迭代次数与额度上限重试；触顶仍不达标 → 停下报老板，由老板裁决是否修订口径、启用 P4、或判「不达标」（**不得自行改口径或放松阈值**）。
- **阻塞**：额度不足、老板输入未到位、或冻结面冲突无法解 → 判「阻塞」，如实记录，不硬跑。

**关键输入清单（最晚到位时间）**

| 输入 | 用于 | 最晚到位 |
|---|---|---|
| M 清单执行结果（老板按固定浏览器与分辨率执行留痕） | P1 | P1 收口前 |
| ≥5 张真实简历图 + 字段标准答案 | P2 | P2.1 开工前 |
| 三项输入（服务端平台 / 第三方 OCR 或视觉服务 / 密钥托管） | P4 | P4 开工前（仅启用 P4 时） |
| ≥5 份简历样本 | P6 | P6 开工前 |

**边界（本方案不做）**：账号与云存储、上线 / 商业化相关项；`utils → components` 跨层依赖不排期，仅记录。

**贯穿所有阶段的纪律**：按 `AGENTS.md` 门禁收口（四项全绿并粘贴实测原文、用例数不低于当时动态基线、声称改变指标的优化项动手前先有改前基线、低于噪声阈值写「无显著变化」）。
